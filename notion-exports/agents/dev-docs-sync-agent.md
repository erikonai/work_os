## Sources of truth

## Sync workflow

1. **Inventory the source first, independently of what Notion already has.** This ordering is the point: an inventory built from the existing page list can only confirm pages that exist and will never surface a source doc that has no page.
   - **API side:** `list-specs` for the spec list, then `search-endpoints` with a broad pattern for the full endpoint inventory across every spec in one call.
   - **Prose side:** sweep [developer.getapril.com](http://developer.getapril.com) by *subject area*, not by the titles of pages that already exist. Run `search` across the integration paths, the data-exchange docs, auth, webhooks, environments, compliance and privacy, support, the product-specific docs, and the reference and recipe namespaces (`ref:` and `recipe:` IDs). Then walk the outbound links inside every doc fetched and add any doc slug they point to that the sweep missed. Repeat until a pass turns up nothing new.
   - Write the resulting source list down before opening Notion. That list, not the page list, is the denominator for this run.
2. **Inventory Notion, then map source to page.** SQL-query this knowledge base's data source for pages tagged Developer Documentation (url, Page, Last edited time). Map in that direction, every source item to its page. Then reverse the map to catch pages with no source. Never build the map page-first.
3. **Gaps and orphans.** A spec or doc with no page is a gap: propose the new page, create only after the user confirms. Propose gaps in priority order rather than as one undifferentiated batch. A page with no source match is an orphan: flag it, never delete it.

> 🚨 **Confirm by ID before calling anything an orphan.** The getapril `search` tool misses docs that `fetch` retrieves fine by ID. On 2026-08-04, `getapril/paycheck-estimation` and `getapril/paycheck-estimation-copy` returned nothing when searched by their own titles, and both pages were nearly retired as orphans on that miss. A search miss is inconclusive. Take the source ID recorded in the page's Change Log and `fetch` it directly; only a failed ID fetch is evidence a doc is gone.

> ℹ️ **Large source docs.** `getapril/data-in` is roughly 97,000 characters and exceeds the fetch tool's token limit. The tool writes it to a local file instead; read it in sections from there. Where a page mirrors only a slice of a large source doc, say so in a page-scope callout, so a later run does not read the partial mirror as drift.

4. **Diff API pages.** For each spec, pull the endpoint inventory (`search-endpoints`, then `get-endpoint` for detail) and compare against the page: endpoints added or removed, parameter or schema changes, auth scheme or server changes.
5. **Diff guide pages.** `fetch` the matching doc and compare substance: steps, code snippets, URLs, environment names, product names. Wording differences with the same meaning are not drift; do not churn pages for style.
6. **Apply updates.** Targeted `update-page` content edits on the drifted sections only, never a full-page replace. Preserve internal-only callouts untouched. Every page ends with a **Change Log** section (heading `## Change Log`). Each sync appends one dated entry there: `**<date>** Synced from <spec title or doc URL>.` followed by a bullet per change, or `Verified against source, no changes.` The Change Log is append-only: never rewrite or delete earlier entries, and never edit above it except for the sync changes themselves.
7. **Log the run.** Append an entry to the Sync Log below: date, pages checked, pages updated (with one-line reasons), gaps, orphans, and anything left for the user.

## Rules

> ✅ The agent may apply factual updates from the source autonomously: endpoint tables, parameters, auth schemes, URLs, code snippets, environment names. These are mirror corrections, not judgment calls.

> 🚨 **Always ask before:** creating a new page, retiring or restructuring a page, changing anything inside an internal-only callout, or resolving a case where source and Notion disagree in meaning rather than detail (that usually means the source doc is stale, which is worth surfacing rather than silently mirroring).

> 👥 **Source-side defects route to the Solutions Consultant team (user-set, 2026-08-04).** Anything wrong in the source rather than the mirror belongs to them: a doc that contradicts itself, a spec carrying a duplicated or scaffold endpoint, a stale or wrong figure, a broken link, a typo. The agent never edits the source. It records each defect on the affected page in a flagged callout, lists it in the run report's Human queue with **Solutions Consultants** as the owner, and repeats it in the Run Log entry. Carry any defect that is still open forward into the next run's queue rather than dropping it, and say how many runs it has been open. Defects touching a number a partner could be quoting (consent scope, retention windows, rate limits, SLAs) are marked blocking.

- **Internal-only content**: anything Notion adds on top of the public docs (partner notes, internal caveats, links to private pages) lives in a callout starting with **Internal:**. Sync never edits or removes these callouts.
- **Retirement policy (user-set, 2026-07-15): note it, never delete it.** A retired page gets a **Retired** callout at the top (date, reason, kept for historical reference) plus a Change Log entry. A retired block inside a live page gets a **Retired content** callout directly above it. Orphans follow the same path once the user confirms retirement; until then they stay flagged in the Sync Log.
- One page per edit batch, so a failed run leaves at most one page half-updated.
- Page edits are targeted `update_content` replacements or `insert_content` appends, never a full-page replace. If a page has drifted so far it needs a rewrite, stop and propose it to the user instead.

Still run ad hoc after an API release or a [developer.getapril.com](http://developer.getapril.com) refresh. Each run should leave a short human queue (gaps to approve, orphans to decide, meaning-level conflicts), never a silent full rewrite.

> ⏰ **The cron does not follow daylight saving.** `0 21 * * 2` is fixed UTC, which is 5:00 PM ET while the US is on EDT and **4:00 PM ET once EST starts in November**. Shift it to `0 22 * * 2` at the November changeover and back to `0 21 * * 2` in March, or accept the one-hour drift.

> 🚨 **The cloud routine cannot reach the source the way a local run can.** The getapril MCP server (`list-specs`, `search-endpoints`, `get-endpoint`, `search`, `fetch`) is a local server, not a [claude.ai](http://claude.ai) connector, so it is not attached to the scheduled run. Only Notion is. Until getapril is added at [claude.ai/customize/connectors](https://claude.ai/customize/connectors), the weekly run has **no path to the source at all**. **Corrected 2026-08-04 by the first scheduled run, which actually tested this.** The original text here predicted that the run "falls back to WebFetch and headless chromium against the public docs site, which covers the prose docs but probably not the 14 OpenAPI specs." That was a prediction written by a local session that could not observe the cloud environment, and it is false. Both are unreachable: the WorkOS environment's egress policy permits outbound HTTPS only to Notion, Gmail and Linear, so WebFetch returns 403 and headless chromium returns `ERR_TUNNEL_CONNECTION_FAILED` for every external host, verified against a control host as well as the docs site. Restoring coverage needs **both** the connector, for the 14 specs, **and** an egress allowance for [developer.getapril.com](http://developer.getapril.com), for the prose docs. Neither alone is enough. The routine prompt instructs it to report those pages as **unverified** rather than write a false "verified, no changes" line. Treat a weekly run as partial coverage until the connector exists, and keep running the API side locally.
